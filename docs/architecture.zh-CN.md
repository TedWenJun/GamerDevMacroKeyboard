# W909 宏键盘：信号实测与 Win11 系统层架构

[English](architecture.md) | 中文

> 本文记录调研与设计决策（阶段一 2026-09-17，2.4G 与背光补充于 2026-09-19）。设备：SXS-W909（固件标识 `YXT K100 Kbd`），USB 有线与 2.4G 接收器 · 系统：Windows 11 Pro 26200

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 需要刷固件吗？ | **不需要**。出厂固件 + PC 端 MacroHub 已能实现"每个物理键 → 任意功能"，且不影响主键盘。 |
| 出厂固件发什么？ | 数字/符号键发 **小键盘键码**（Num0–9、Num.、Num+、Num-、Enter、Space），摇杆发方向键，旋钮左右旋发 Consumer 音量±；旋钮按下**不发任何键码，只在厂商位图中上报（位 42）**，是一个天然的纯可编程键。 |
| 能区分宏键盘和主键盘吗？ | 能。MI_02 下的**厂商集合 FF00** 会实时上报"物理按键位图"，每个物理键对应唯一一位；该集合 Windows 不独占，用户态可直接 `ReadFile`。 |
| 能拦截宏键盘的原始按键吗？ | 能。厂商位图报告比 `WH_KEYBOARD_LL` 回调**早 1–2 ms**（128 次实测，中位 1 ms，最大 2 ms），钩子据此判定并吞掉。 |
| 固件有"模式"吗？ | 有。**旋钮按下切换固件模式**：切换后 1–6 键从 Num1–6 变为 `A–F`（其余键待测）。厂商位图位号不随模式变化，因此 MacroHub 以位图为物理身份，拦截采用"物理按下后 25 ms 内的任意硬件按键"通配匹配，与模式无关。 |
| 旋钮音量能拦截吗？ | **不能**（实测）。Consumer 音量 usage 由系统直接处理，完全不经过键盘钩子。旋钮仍可触发任意功能，但系统音量会同时变化；建议把旋钮绑定音量类功能，或日后通过固件改键解决。 |
| 资料里的 "Raw Input 判断设备再拦截" 可行吗？ | **不可行**（实测）。`WM_INPUT` 总是晚于 LL 钩子，钩子拦截后 `WM_INPUT` 也不会产生。 |
| 资料里的 "F13–F24 给 UE 绑定" 可行吗？ | **UE 不认**。UE5 `WindowsPlatformInput.cpp` 只映射到 F12，F13–F24 在 UE 中无对应 `EKeys`。UE 侧应走 MacroHub 的 IPC 转发（阶段二插件）。 |

## 2. HID 接口实测

VID `B6A4` / PID `4100`（2.4G 接收器为 PID `4101`，集合完全相同），复合设备 3 个接口 7 个集合：

| 集合 | Usage Page / Usage | 报告 | 用户态可读 | 用途 |
|---|---|---|---|---|
| MI_00 | 0x01 / 0x02 鼠标 | 8B | ✗ 系统独占 | 未观察到使用 |
| MI_01 | 0x01 / 0x06 键盘 | 9B boot | ✗ 系统独占 | **实际键码来源** |
| MI_02 COL01 | 0x0C / 0x01 Consumer | RID3, 16bit usage | ✓ | 旋钮 VolumeUp `0xE9` / VolumeDown `0xEA` |
| MI_02 COL02 | 0x01 / 0x80 System | RID4 | ✓ | 未观察到使用 |
| MI_02 COL03 | **0xFF00 / 0x01 厂商** | RID5, 24B 输入 | ✓ | **物理按键位图** |
| MI_02 COL04 | 0xFF01 / 0x01 厂商 | RID6, 40B Feature | ✓ | 厂商配置通道：背光写入与电量查询，见 [设备协议](device-protocol.zh-CN.md) |
| MI_02 COL05 | 0x01 / 0x06 NKRO 键盘 | RID7 位图 | ✗ | 未观察到使用 |

`GET_INPUT_REPORT(5)` 返回 `A1 01 05 01 02 00 …" K100 Kbd"`（固件信息串）。

## 4. 时序实验

`tools/HookOrderTest`（SendInput 注入）与 `tools/InputRecorder`（真实硬件）得到一致结论：

```
物理按下 ─┬─► HID 类驱动 ─► 厂商集合 FF00 ReadFile 返回          t0
          │                  Consumer 集合 ReadFile 返回          t0
          └─► kbdhid ─► win32k RIT ─► WH_KEYBOARD_LL 回调        t0 + 1~2 ms
                                     └─(钩子放行)─► WM_INPUT       之后
                                     └─(钩子拦截)─► 无 WM_INPUT
```

## 5. 系统层架构（MacroHub）

```
┌────────────── W909（出厂固件，无需刷写）──────────────┐
│ 键盘 MI_01（小键盘码） 厂商 FF00（物理位图） Consumer（旋钮） │
└───────┬───────────────────────┬──────────────┬─────────┘
        │ 系统独占                │ 直接 ReadFile │
        ▼                         ▼              ▼
  WH_KEYBOARD_LL 钩子 ◄──关联── PadHidReader（物理信号 → 控件 ID）
  （只负责吞掉原始按键）              │
        │                             ▼
        │                   Router：层 → 功能 → 应用档案
        │                             │
        │            ┌────────────────┼──────────────────┐
        ▼            ▼                ▼                  ▼
  主键盘照常   ActionExecutor     WebSocket 转发      Web 配置界面
               SendInput 快捷键   function 事件       (127.0.0.1:17900)
               文本/宏/程序/鼠标  → UE 插件等应用
```

**三层配置模型**（`hub.json`）：

1. **设备层** `device.controls`：控件 ID（K1…KSPACE、KNOB_CW/CCW/PRESS、JOY_*）↔ 硬件签名（`vendor:48`、`key:61`、`consumer:0E9`）。换设备只改这一层。
2. **系统层** `functions` + `layers`：功能是与硬件、应用都无关的语义命令（`ue.play`、`edit.copy`…），带默认动作；层把控件映射到功能。
3. **应用层** `apps`：按前台进程匹配（支持 `*` 通配），可自动切层、覆盖某功能的动作、或把功能**转发**给已连接的应用客户端（连接时由应用原生处理，断开时回退本地快捷键）。

**关键设计**：动作由"物理信号"触发，钩子只负责吞键。因此不产生键码的控件也能用；即使偶发拦截失败，也不会重复触发功能（Hub 会统计并提示"泄漏"）。

**拦截模式**（`suppression`）：`correlate`（默认，出厂固件，有线与 2.4G）/ `codes`（键码独有时，如固件改为 F13–F24，或没有厂商通道的连接方式）/ `off`。

**旋钮转动帧**：旋钮每转一格，固件先发送一份全零的厂商位图，约 1 ms 后才发送音量报告。按住旋钮旋转时，这会让“旋钮按下”位看起来已松开，而真正的松开报告又与上一份相同（位图差分看不到变化）。`PadHidReader` 把“旋钮按下的松开之后 10 ms 内紧跟旋转”识别为转动帧，保持按下状态，直到出现不跟随旋转的全零报告。

## 7. 已知限制与后续

- **2.4G 接收器**：已验证（PID `4101`），按键、旋钮、背光、电量与有线一致。键盘休眠时不应答状态查询，Hub 在下一次按键唤醒后立即补查电量。
- **蓝牙模式**：未验证；默认匹配已包含蓝牙 HID 路径格式，若无厂商位图通道，改用 `codes` 模式。
- **管理员窗口**：非管理员运行时 SendInput 无法作用于管理员权限窗口（UIPI），需要时以管理员身份运行 MacroHub。
- **厂商配置通道 FF01**：MacroHub 只用于背光和只读状态查询，从不修改键盘的按键映射。
- **阶段二 UE 插件**：通过命名管道 `\\.\pipe\MacroHub` 注册（协议 v2，见 [protocol.md](protocol.md)），接收原始控件事件，按编辑器上下文映射到原生 API / Editor Command / PIE / Enhanced Input，见第 8 节。

## 8. MacroHub 与 UE 插件的职责划分

UE 内的快捷键语义取决于**编辑器焦点**：同一个旋钮在 Sequencer / 动画编辑器中应拖动时间轴，在动画蓝图中切换子标签页。这些标签页多为同一进程、同一窗口内的 Slate 控件，进程外的 MacroHub 看不到，因此：

| | MacroHub（系统层） | UE 插件（应用层） |
|---|---|---|
| 职责 | 硬件识别、原始按键拦截、按前台进程分发、插件离线时的回退、旋钮音量保护 | 判定 UE 内上下文（编辑器类型、PIE / Editor / Standalone）、上下文 → 行为绑定、调用原生 API 执行 |
| 发给对方 | 原始控件事件 `control`（带 `seq`、`t`、`kind`、`part`） | 当前上下文 `context`（用于配置界面显示） |
| 配置位置 | Web 界面：系统层与非 UE 应用 | UE 编辑器设置：各编辑器上下文的绑定 |
| 执行方式 | 模拟快捷键（仅回退时） | 原生 API，如 `ISequencer::SetLocalTime`、基于 `ITimeSliderController` 的时间轴 |

对应实现：应用档案 `forward = controls`（UE 默认）——插件在线时 Hub 跳过自身层、只转发原始控件并拦截原始按键；插件离线时回退到 Hub 的“UE 编辑器”层快捷键。

**传输选择**：实测 WebSocket 本机往返中位 0.11 ms / p99 0.24 ms（2000 次），传输不是瓶颈；延迟与稳定性取决于 UE 端何时在游戏线程处理（UE WebSockets 模块回调在游戏线程 tick 中派发，最多晚一帧）。因此新增**命名管道**通道 `\\.\pipe\MacroHub`（按行 JSON、仅当前用户、无端口、断线即知，UE Core 自带 `FPlatformNamedPipe`），WebSocket 保留给配置界面与脚本。UE 端建议：后台线程阻塞读 → 无锁队列 → 游戏线程每帧开头统一派发。

**PIE 注意**：PIE 与编辑器同进程同 pid，由插件在进程内区分；`UnrealEditor.exe -game` 独立进程 pid 不同，客户端登记 pid 后 Hub 按 pid 精确匹配。PIE 视口会吞掉模拟快捷键，所以 PIE 场景必须走插件通道。

**硬件限制**：旋钮在所有固件模式下都发送 Consumer 音量±，系统音量变化不可拦截；Hub 通过 Core Audio 端点通知在保护窗口内恢复音量（`knobVolumeGuard`），代价是音量提示可能闪现。
